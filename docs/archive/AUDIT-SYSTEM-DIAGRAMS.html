LLDInternals

How the machine actually works inside: the finding lifecycle, the dedup decision tree, prompt assembly order, the finding record schema, and the severity matrix.

1 — Finding lifecycle (state machine)

stateDiagram-v2 [*] --> open : filed by agent open --> fixing : fix started open --> wontfix : accepted risk fixing --> fixed : PoC no longer reproduces fixing --> fixing : PoC still reproduces fixed --> verified : independent re-run passes fixed --> fixing : verifier rejects verified --> [*] wontfix --> [*]

Rule: a finding only closes at verified — "fix written" is not done. Registry history is append-only; statuses change, past entries never do.

5 — Severity matrix (impact × likelihood — no gut feel)

Likelihood: HighMediumLow
Impact: CriticalCriticalCriticalHigh
Impact: HighCriticalHighMedium
Impact: MediumHighMediumLow
Impact: LowMediumLowLow

Impact: Critical = RCE / unbounded fund drain / account takeover at scale. High = ~₹3,000/burst drain, impersonation, single-key RCE. Likelihood: High = unauthenticated remote or trivial; Medium = one user interaction; Low = physical access or stacked preconditions.
Example: BMA-01 (no max_tokens cap) = High impact × High likelihood → Critical by matrix. It was filed as High — the auditors under-scored by one notch.
