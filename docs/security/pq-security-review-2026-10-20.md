# PQ pairing security review — 20 October 2026

**Decision: keep PQ disabled by default.** The implementation issues found in this internal review have been remediated and regression-tested. This review was performed by the implementation author; it is not independent cryptographic sign-off, a formal proof, FIPS validation, or physical-device validation.

## Scope and method

Reviewed the ML-KEM backend and failure paths, KEM-to-PSK derivation, canonical QR/transcript bytes, IKpsk0 token processing, M1/M2 correlation, one-time prekey use and retries, confirmation/transport state, trust replacement and revocation, session budgets, persistent phone trust, and asynchronous mobile pairing/reconnect/cancellation. Relay routing and real WebSocket/Cloudflare interoperability are exercised by the existing integration suites.

The attacker model includes an untrusted relay that can observe outer envelopes, alter framing, replay/delay messages, and route packets under misleading identifiers; a formerly trusted phone retaining its private keys; malformed KEM/Noise input; concurrent legitimate attempts; failed RNG/backend operations; and local clock adjustment. A live endpoint compromise and JavaScript runtime side-channel resistance are outside the guarantees of this implementation.

Six failing regression tests were captured before the fixes: [original failure evidence](../../artifacts/crypto/pq-security-review-before-tests-2026-10-20.txt). Additional adversarial tests were added during remediation. The test implementation is [security-review-test.mjs](../../packages/core/test/security-review-test.mjs); the existing crypto/vector suite remains [pq-test.mjs](../../packages/core/test/pq-test.mjs).

The new regression file contains 15 tests, including mutation coverage, authenticated correlation checks, exact/crossing byte limits, cancellation/trust identity helpers, and clock rollback. Six original failures are retained as evidence; this does not imply that every added test was run against the original build.

## Cryptographic construction assessment

No KDF/domain-separation or Noise token-order defect was found in the reviewed composition. The QR commits to the raw ML-KEM-768 encapsulation key through SHA-256. The canonical advertisement, fixed suite/domain, and KEM ciphertext enter the prologue and domain-separated HKDF-SHA256. The resulting 32-byte PSK enters Noise through `psk0` before the first encrypted static field/proof; both `e` tokens also mix key material. The final M2 payload, including the new M1 correlation value, is authenticated by Noise.

Evidence includes selected NIST ACVP fixtures, bidirectional ML-KEM interoperability with Node/OpenSSL, the independent Python IKpsk0 ciphertext/transcript fixture, and the independent Python product-KDF fixture. These demonstrate conformance for the selected inputs; they do not prove the security of the complete product composition. The construction remains a custom protocol requiring an external cryptographic review.

The explicit nonce remains authenticated through AEAD nonce selection. The review did not add redundant nonce AAD or change the ciphertext format. Existing routing bindings remain authenticated inside transport plaintext. Ordering remains the documented high-water policy, accepting forward gaps and rejecting replays/late lower nonces. An adversarial relay can still suppress delivery or force availability failures; this work does not claim relay-resistant availability.

## Validation

Run the complete review and regression checks with:

```sh
npm run check
```

Or run both crypto-specific suites with:

```sh
npm run pq-test
```

The complete check includes typecheck, lint, 15 original PQ/vector regression groups, 15 additional review tests, 47 gateway tests, the mobile/relay/security suites, 14 desktop WebSocket integration cases, and actual Workers/Durable Object runtime checks. No provider credentials or production deployment are needed.

The machine-readable receipt records tool/runtime versions and results. [Review receipt](../../artifacts/crypto/pq-security-review-2026-10-20.json).

The wire hardening is an update to an experimental, disabled feature: previous experimental PQ clients that send the exposed static-key field or omit M2 correlation are intentionally incompatible. Update phone and desktop together before trials. No fallback to classical pairing was added for a PQ advertisement or persisted PQ trust record.

## Remaining enablement gates

1. **Independent review is still required.** This author review is not independent assurance. The KEM-to-PSK composition, transcript encoding, authorization state machine and backend interfaces need external scrutiny before production opt-in.
2. **The JS backend is not constant-time and erasure is best effort.** The installed Noble documentation makes no constant-time claim and says the package has not received an independent audit. A reviewed native backend remains necessary for a stronger local side-channel threat model; overwriting owned buffers cannot erase every JIT/GC copy.
3. **Physical/runtime validation remains outstanding.** iOS/Hermes, Android/Hermes and browser measurements and end-to-end tests were not performed here. Include suspend/resume, secure storage, cancellation, reconnect loss, and monotonic-clock behavior on the actual shipped runtimes.
4. **The overall application's dependency scan is not clean.** The scan returned 21 advisories (18 high, 3 moderate), involving the existing Expo/Metro/React Native dependency graph. No `@noble/*` advisory was returned by that scan. SDK/toolchain remediation is separate from these PQ code fixes and remains an application release concern; absence of a registry advisory is not proof of cryptographic safety.
5. **Guarantee boundaries remain unchanged.** Client authentication is still classical, a desktop restart discards memory-only PQ prekeys, expired/missing reconnect material requires a fresh scan, and periodic refresh is not a post-compromise ratchet.

The default `enablePqPairing` setting remains `false`. This review has not enabled PQ or deployed any service.
